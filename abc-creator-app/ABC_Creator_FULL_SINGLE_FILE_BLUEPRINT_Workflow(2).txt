SECTION 9 — CREDIT SYSTEM
================================================================================

Credits are the internal currency for AI generation.

Purpose:
- control usage
- prevent abuse
- support paid plans
- cover AI provider costs
- prevent unlimited free generation

Core credit rules:
- Frontend displays estimated cost only.
- Backend decides real cost.
- User cannot send cost from browser.
- Tool cost must come from server-side registry/config.
- Credits must be reserved before AI call.
- Successful generation marks reserve as spent.
- Failed generation refunds credits.
- Race conditions must be prevented with database transaction/row lock/RPC.
- Credits are operational records, not saved output records.

Recommended free plan:
Free = 10 lifetime credits only

The exact free credit amount is still user decision if changed later. Earlier reference suggested 10 lifetime credits, and this is recommended because it reduces free-credit farming.

Paid plans:
Exact monthly credits and pricing can be finalized later with Stripe. Do not blindly trust old pricing unless user confirms. However, possible concept:
- Free: lifetime credits only
- Starter: small monthly credits
- Plus: medium monthly credits
- Pro/Agency/Business: higher monthly credits
- Bundle/yearly: special allocation if confirmed

Credit flow:

1. User clicks Generate.
2. Backend checks Supabase session.
3. Backend checks profile status.
4. Backend checks anti-abuse/account review status.
5. Backend reads authoritative tool cost.
6. Backend starts atomic credit reservation.
7. If balance insufficient, return INSUFFICIENT_CREDITS.
8. If enough, reduce available balance/reserve credits.
9. Backend calls AI provider.
10. If success, mark reserved credits spent.
11. If failure before usable output, refund credits.
12. Return/stream output to user.
13. Do not save output.

Race condition example:
Bad:
- user has 10 credits
- opens 3 tabs
- all see 10
- all generate
- user overspends

Good:
- database transaction locks balance
- first request reserves 6
- second request sees updated balance
- no overspending

Credit transaction types:
- grant
- subscription_grant
- reserve
- spend
- refund
- adjustment
- expired
- chargeback_reversal

Credit transaction statuses:
- pending
- reserved
- spent
- refunded
- failed
- cancelled

Refund policy:
Refund if:
- provider call fails before usable output
- backend validation fails before provider call
- request is cancelled before provider call starts
- system error prevents output

Do not refund automatically if:
- output is successfully generated but user dislikes it
- user closes tab after generation succeeded
- user enters poor input and receives valid output
- result is generated and displayed

Optional UX:
- show current balance in dashboard/header
- show tool cost on tool card/form
- show insufficient credits modal
- show upgrade button if paid billing exists

SECTION 10 — ANTI-ABUSE SYSTEM
================================================================================

Anti-abuse is required.

Reason:
Free credits can be farmed with fake accounts, temp emails, VPNs, repeated OAuth accounts, multiple browsers/devices, bots, and direct API calls.

Anti-abuse does not conflict with no-history rule because it does not store generated content. It stores operational security signals.

Primary goals:
- stop unlimited free-credit farming
- stop temp-mail abuse
- stop bot signup/generation spam
- stop repeated account creation
- stop direct API misuse
- protect provider keys and costs
- keep normal users smooth

Checks worth implementing:
- email verification
- OAuth trusted provider check
- CAPTCHA/Turnstile on signup and maybe generation if abused
- disposable email domain detection
- IP hash, not raw IP when possible
- signup velocity checks
- repeated free-credit grants per cluster
- VPN/proxy/Tor risk detection if using a provider
- account review/block flag
- user agent / browser risk signal
- optional fingerprint hash if legally/privacy appropriate
- direct API session checks
- backend cost validation
- rate limiting per user/IP

Free-credit grant gate:
Free credits are granted only after:
1. user exists
2. email verified or trusted OAuth
3. profile bootstrap succeeds
4. disposable email check passes
5. CAPTCHA/Turnstile passed if enabled
6. IP/proxy risk acceptable if provider enabled
7. signup velocity acceptable
8. duplicate abuse cluster not detected
9. account not blocked/review
10. credit grant inserted idempotently

If suspicious:
- account may exist
- free credits may be withheld
- account may be marked review
- generation may be blocked if risk is high

Decisions:
allow:
- grant free credits and normal access

review:
- allow account but do not grant free credits yet
- show account review/verification message if needed

block:
- block generation/free credits
- possibly disable account

Data privacy:
- avoid storing raw IP long-term if possible
- store hashed IP
- disclose anti-abuse data in privacy policy
- do not store generated content
- do not store user prompts unless needed for immediate request

Abuse scenarios:
1. Temp email signup:
   block or review free-credit grant

2. VPN/proxy high risk:
   review or block free-credit grant

3. Same fingerprint repeatedly:
   no duplicate free grant

4. Direct unauthenticated API:
   401 AUTH_REQUIRED

5. Browser changes tool cost:
   ignored; backend uses server cost

6. User deletes/recreates account:
   cluster/abuse logic prevents repeated free grants

7. Multiple tabs:
   atomic credits prevent overspend
